zeno · pilot proposal

Decided things
stay decided.

AI writes more code than we can review. zeno checks every request and every change against our decisions and standards first, so less goes wrong and less lands on reviewers.

zeno · open source (MIT) · CLI + Claude Code plugin
What changed

More code, same reviewers.

Before AI: writing code took time, and so did review. They moved at the same pace.

With AI: teams with high AI use merged 98% more PRs, and review time went up 91%. PRs got 154% bigger.

With zeno: code stays fast. Rules, decisions and standards are checked before review, so people review less by hand. This is the target the pilot measures, not a result yet.

"With AI" numbers: Faros AI, AI Productivity Paradox, 2025, telemetry from 10,000+ developers on 1,255 teams. Before-AI bars are the baseline. The zeno bar is a target, not data.

The problem

A decision takes days. Then the next agent breaks it.

How it works

Every non-trivial request passes a gate before work starts.

Each verdict cites the rule or decision it used. When someone overrides a push back, the reason is logged in the repo, and zeno learn suggests rule changes from those logs.

Facts, not assumptions

A request is not a fact. Each claim in it gets checked.

The gate reads data only through tools we already use (MCP, CLI). It runs one or two small read-only queries, and keeps counts, not people.

Where the time goes

Find the conflict before the code, not after.

The later a conflict is found, the more work sits on top of it. The pilot counts how many conflicts the gate catches before code.

The model

Three kinds of rules, two checkpoints.

Why review is the wall

Reviewers check by hand what a machine could check.

A reviewer today checks
  • Is the logic right?
  • Is this what the product needs?
  • Does it follow our standards and layout?
  • Does it cross an architecture boundary?
  • Does it undo a past decision?
  • Does a price or limit now have two values?
  • Was the reason for it ever true?
With zeno, a reviewer checks
  • Is the logic right?
  • Is this what the product needs?

The other five run before review:

zeno check covers standards, layout, architecture and values with two homes. The weigh gate covers past decisions and the claims behind the request.

Where it fits

Many tools give agents context. Few enforce decisions.

Copilot org instructions give one set of rules to every repo. Nothing checks that work follows them.

Wiki and Q&A tools (AutoWiki, DeepWiki, Unblocked) describe code and find context. They don't block anything.

Qodo gates code quality, not product decisions.

zeno sits beside them and adds the missing step: stop work that breaks a decision.

The pilot

4 weeks · 3 repos · 1 person · on a branch

Out of scope: a hosted site, an editor, other people's laptops, CI changes on main, new paid services, and data going anywhere it doesn't already go.

Risks and safeguards

Small, local, and easy to undo.

Our data

zeno runs no servers and sends nothing itself. The gate runs inside Claude Code, so it's only used where Claude Code is already approved.

Our repos

All zeno files sit on a branch. Nothing merges without the repo owner's OK.

Slower work

Time cost is measured. If the gate costs more than it saves, the pilot fails, and we say so.

Wrong verdicts

Every verdict cites its source, so a wrong one is easy to spot. Overrides are logged, and zeno learns from them.
