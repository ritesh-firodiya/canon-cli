# Default pipeline
**Choice:** the default flow is `intake → (problem | idea | discovery) → research → options → design → plan → feature → code → review → release → outcome`. Problem, idea and discovery fork from intake: any of them, in any order, or none, each optional with a `when:`. A stage's `after: [ids]` names the stages it may follow, which makes forks; with no `after:` it follows the stage above it, so a plain list stays a line. A stage named for a default inherits its wording but not its place. Work starts at `started-at:`, else the stage named for its kind (done by the page), else the first stage; a trigger's problem starts at the first stage. Every stage checks that what it was given is true before using it. The layout is in the `context-layout` standard.
**Why:** canon ships one full template that teams change, and a team can only change what the schema can say: a straight list could not let work begin as an idea and open a problem after it. The old words were wrong: `idea` named both the starting idea and the weighed options, `result` was the `outcome:` field under another name, and design came after the plan it should inform. Signals arrived as claims, and only stages with `verify:` checked them.
**Rejected:** a linear default with optional stages (cannot express any order among problem, idea and discovery) · an `any: [...]` group (cannot say "idea only after a problem") · both `any:` and `after:` (two ways to say one thing) · signals as a record kind (a `source:` field already holds them) · `solutions` (options are not proven) · aliases for old ids (an MVP with no outside users; each product's ids were renamed instead) · experiments writing skip entries for earlier stages (`started-at:` already says where they begin).
