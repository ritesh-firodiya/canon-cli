zeno · how it works

Better decisions.
Lighter reviews.

AI writes code fast, but our knowledge is scattered and review has become the wall. zeno brings what we know into the repo, checks every request against it, and enforces our standards before review.

Where the time goes

AI cut the time to write code. Review time went up.

No AI: most of the time went into writing code. Review kept pace.

With AI: writing is fast, but review time went up 91% and PRs got 154% bigger. Review is now where the time goes.

With zeno: rules, decisions and standards are checked before a person looks. The target is review time back down. Not measured yet.

Review +91% and PR size +154%: Faros AI, AI Productivity Paradox, 2025 (10,000+ developers, 1,255 teams). Other bar heights show direction, not measured values.

The problem

Our knowledge is in six places. Each AI session sees a slice.

zeno doesn't connect to Gmail or Confluence itself. We export a source, or pull it with the AI tools we already have, into .context/raw/, and ingest turns it into wiki pages. After that, every session finds it with local search.

How it works · the parts

Three parts. Everything they read lives in the repo.

How it works · one request

What happens between "build this" and the merge.

1 · SESSION STARTS

The hook loads our principles and refreshes the local search index.

2 · YOU ASK

"Add a manual expense button. Users keep asking for it."

3 · WEIGH

Searches decisions and the wiki, checks each claim, reads data sources, weighs cost vs value. Big requests get a second opinion.

4 · VERDICT

Do it, do it differently or push back, citing every rule and fact it used.

5 · BUILD

The agent searches our wiki and the current vendor docs before it writes code.

6 · RECORD

A new decision becomes a record in wiki/decisions/ with /zeno:decision.

7 · CHECK

zeno check runs before the PR and in CI. A broken hard rule fails the build.

8 · LEARN

Overrides are logged with reasons. zeno learn proposes rule changes from them.

Steps 3, 4 and 7 are where zeno says no. Every other step makes the agent better informed.

How it enforces

It asks for facts and guides you. It stops only on hard rules.

A real verdict

What a push back looks like.

The request asked for a manual entry button, "because users keep asking".

The gate found a decision against manual entry, no feedback on file, and no retention metric.

So it stopped and gave three ways on: bring the facts, change the rule on written terms, or drop it.

Without zeno, this would have been built, then argued about in review.

Make it ours

We set the rules: our templates, our stack, our sources.

TEMPLATES

ADR, RFC, PRD, spec

Page types with the sections we require. A missing one fails zeno check.

DATA SOURCES

Datadog, Snowflake, Sentry

Read through the MCP servers or CLIs we have. Read-only, small queries.

TECH STACK

Current vendor docs

Packs index React, Next.js, Firebase docs and more, so agents don't guess old APIs.

ARCHITECTURE

Import rules per repo

Layers in .dependency-cruiser.cjs. A broken boundary or a cycle fails the build.

DOMAIN

One home per value

A price or limit lives on one page. The same number elsewhere fails the build.

OUR CHECKERS

Lint, schema, design

Scripts we already have run inside zeno check.

# company .claude/zeno.yaml, every repo inherits estate: true standards: [.zeno/standards] wiki: types: - type: prd folder: prds sections: [Problem, Goals, Non-goals, Metrics, Open questions] commands: - id: lint run: pnpm lint # one repo's .claude/zeno.yaml kind: web modules: [docs, knowledge, code, architecture] packs: [nextjs, react, firebase] checks: stale-copies: enabled: false reason: "Cursor still used here"

A repo overrides with a written reason, shown in every run. Section names are examples.

Getting started

A repo is ready in an afternoon.

# once per laptop npm install -g @freetesh/zeno claude plugin marketplace add ritesh-firodiya/zeno claude plugin install zeno@zeno zeno doctor # node, git, local search # once per repo, on a branch zeno init # config + .context/ /zeno:ingest .context/raw/checkout-prd.md /zeno:decision No manual entry — why… zeno sync # index for search zeno check # then add it to CI
  • Install: the CLI and the Claude Code plugin. Search runs locally.
  • Set up: zeno init asks the stack and modules, then writes the config and folders.
  • Bring knowledge in: export the PRDs, RFCs and notes we have, and ingest them.
  • Write the top 5–10 decisions with the repo owner, about an hour.
  • Turn on the check locally first, then in CI.
